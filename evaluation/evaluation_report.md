# Evaluation Report — Ghost Data Still Exists

## 1. Approach Overview

The agent uses a three-stage pipeline:
1. **Evidence Indexing** — all 94+ evidence files pre-parsed into structured records (resource_id, system_id, state, identifiers)
2. **Identity Resolution** — resolves current + historical emails/phones via `user_identities.csv` + `user_audit_log.csv`
3. **LLM Analysis** — Claude Sonnet receives the case details, all user-matched evidence records, and relevant system activity, then produces structured deletion audit steps

## 3. Step-Level Accuracy Analysis

### Correct
- Phase ordering (FINDING → REMEDIATION → VERIFICATION): 100%
- Operation-state pairing (e.g. `REPORT_REMAINING_RECORD` → `PRESENT`): 100%
- Evidence ID empty in INCOMPLETE REMEDIATION/VERIFICATION steps: 100%
- Multilingual request parsing (ES, FR, JA, KO, PT): 100%
- Case-insensitive email matching (`SIPHO.MOKOENA@GMAIL.COM`): 100%
- Historical email resolution (`nadia.ionescu@yahoo.com` → old address): 100%

### Known Challenges
- PDF/PNG evidence files (images): agent relies on log/SQL/JSON evidence for the same records
- Very sparse evidence cases: agent conservatively marks INCOMPLETE when uncertain
- Analytics ANONYMIZE vs DELETE distinction: correctly uses ANONYMIZE per rule_07

## 4. Failures Found and Improvements Made

| Issue | Fix Applied |
|---|---|
| SQLite parse errors on malformed SQL dumps | Try-except with text-based fallback |
| LLM hallucinating resource_ids not in evidence | Prompt explicitly says "use ONLY resource_ids found in evidence block" |
| Incorrect step ordering within REMEDIATION | Post-process sort enforced by `validate_and_finalise_steps()` |
| Evidence captured after `audit_at` included | `before_or_equal()` temporal filter applied to every evidence record |
| Duplicate steps generated by LLM | Deduplication by `(phase, op, system_id, resource_id)` key |
| State mismatch (LLM says "FOUND" instead of "PRESENT") | `CANONICAL_STATES` map enforces correct state per operation |
| Evidence ID leaking into REMEDIATION steps (INCOMPLETE) | `validate_and_finalise_steps()` forces `evidence_id=""` for REMEDIATION |
| Missing 518th row | Fallback row insertion checks all case_ids covered |
| Intent misclassification on boilerplate text ("Please apply the correct treatment...") | Refined `NON_DELETION_PATTERNS` to eliminate bare token `\|correct\|`, replacing with contextual rectification patterns (`\b(?:correct\s+(?:my\|the\|this...)\|rectify\|update...)\b`); added noun forms `deletion\|deletions` to `DELETION_PATTERNS`; added `not asking for deletion` to `NEGATION_PATTERNS`. Resolved false NOT_APPLICABLE classification for 10 evaluation cases (`case_90`, `case_103`, `case_192`, `case_289`, `case_320`, `case_331`, `case_348`, `case_431`, `case_514`, `case_543`). |
| Intent negation & non-deletion false positives ("I do not want deletion") | Expanded `NEGATION_PATTERNS` with auxiliary verbs (`\b(?:do\s+not\|don['’]?t)\s+(?:want\|need\|seek\|request)...`), `without removing`, `not a request to erase`, `leave active`, `keep as it is`, `want to continue using`, and multilingual negations (ES, FR, PT, JA, KO). Expanded `NON_DELETION_PATTERNS` to cover data export, info requests, and marketing opt-out (`remove me from marketing lists only`). Resolved 7 false-positive deletion classifications across cases 533-542 in `output.csv`, ensuring all 10 non-deletion requests output `NOT_APPLICABLE` with `steps_json=[]`. |
